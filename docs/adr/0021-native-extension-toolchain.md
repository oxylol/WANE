# ADR-0021: Build the native extension with a pinned godot-cpp, behind one switch, with the GDScript reference kept honest

- Status: Accepted (toolchain only: no simulation code is ported yet)
- Date: 2026-10-20
- BUILD.md sections:
  - 13, Architecture: "C++ via GDExtension for the physics sweep, hitbox resolution, the VFX budget manager and the lighting pass once profiling demands it";
  - 13, Determinism and replays (the golden hashes of every fixture stay what they were, on Linux, Windows and macOS);
  - 13, Testing and CI, Frame budget (the 3.0 ms simulation step that the GDScript core misses: ADR-0020 Decision 8).
- CLAUDE.md: "C++ GDExtension only for profiled hot paths, and a GDScript reference implementation is kept and tested against it"; rule 1 (the core has no Node dependency), rule 2 (integers in 1/256-unit sub-pixels), rule 4 (a desync is a P0 bug), rule 10 (nothing enters the repo from outside it; `docs/LICENSES.md` lists what may).
- Checklist lines (BUILD.md section 15): "The game holds 60 fps in the stress room on the Deck profile" (this ADR is the tool, not the port); "Replay fixtures run headless" and the cross-platform replay line (the native path must not move a hash).

## Summary

- godot-cpp `godot-4.5-stable`, pinned by commit in `native/.godot-cpp-version`, cloned by `ci/setup_godot_cpp.sh` into an ignored folder, never vendored (Decision 1).
- The 4.5 tag, not an API dump of 4.7.2: newest tag at or below 4.7, GDExtension is forward compatible, `compatibility_minimum = "4.5"` (Decision 1).
- SCons 4.10.1 is pinned in `tools/requirements.txt`; `ci/build_native.sh` builds into the ignored `native/bin/`, quiet, non-zero on error (Decision 2).
- `native/`: `SConstruct`, `wane.gdextension` (linux and windows x86_64, macOS universal; debug, release), `src/` with `NativeProbe`, the canary and the pattern (Decision 2).
- One switch, `NativeBackend.use_native()`: off, auto (default) or on, from `WANE_NATIVE` or project setting `wane/native/mode`, read by the `NativeBoot` autoload (Decision 3).
- Mode on with the library absent or stale exits 1; auto falls back to GDScript; the library version must equal `NativeBackend.EXPECTED_VERSION` (Decision 3).
- Native code: int64 and uint32 only, no float, no unordered containers, no time, threads or randomness; `ci/lint.sh` greps `native/src` (Decision 4).
- Every native method has a same-named static in `NativeRef`; `test_native_parity.gd` pins it to independent vectors, sweeps native against it, and fails if one is missing (Decision 5).
- CI builds on ubuntu, windows and macos (godot-cpp cached) and runs fixtures with the switch off and on against the same goldens; lint is unaffected (Decision 6).
- Cold build 285 s on 4 cores, 4 s when nothing changed, debug library 1.9 MB (Consequences).
- Only the engine classes the extension uses are bound (`native/build_profile.json`: `RefCounted`, `OS`): a cold build is about 100 s here and the CI cache is megabytes; the cache is saved right after the build, one key per target (Decision 7).

## Context

BUILD.md section 13 reserves C++ GDExtension for the profiled hot paths, and ADR-0020 profiled them: the stress room's simulation step is p99 9.0 ms against the 3.0 ms budget, and GDScript cannot close that gap (Decision 8 there). Before any hot path is ported the project needs the chain that makes a port safe: a native build that every platform can reproduce, a switch that can fall back to the reference, and a proof that the two agree. CLAUDE.md pins what the proof must show: the reference stays and is tested against the port, and a desync between platforms is a P0 bug.

The doc leaves open which godot-cpp to use. godot-cpp publishes tags only up to `godot-4.5-stable` (checked with `git ls-remote` on 2026-10-20: no 4.6 or 4.7 tag, branches 4.0 to 4.5 and master); the engine is 4.7.2 (`.godot-version`).

## Decision

1. **godot-cpp: the 4.5 tag, not the engine's API dump.** GDExtension keeps binary compatibility forward: a library built against 4.5 loads in 4.7.2 (proved headless here: the extension registers `NativeProbe` and GDScript calls it). The alternative, `godot --dump-extension-api` fed to a godot-cpp master, would bind exactly 4.7.2, but master is unreleased, moves daily, and a rebuilt API dump after an engine bump would silently change the bindings the determinism proof rests on. A tag is a fixed, reviewed interface; when the engine pin moves (ADR-0001 requires a task and a full regression run) the godot-cpp pin is a line in that task. `native/.godot-cpp-version` holds the tag and the commit; the script checks out the commit and fails if the checkout is anywhere else, so a moved tag cannot change the build. godot-cpp lives in the git-ignored `native/godot-cpp` (with a `.gdignore`, so Godot, the compile stage and gdlint never read its test project), is MIT licensed and is listed in `docs/LICENSES.md`. SCons is pinned in `tools/requirements.txt` like every Python tool.
2. **Layout and build.** `native/SConstruct` calls godot-cpp's, adds `native/src/*.cpp` (sorted, so the object order does not depend on the file system) and writes `native/bin/libwane.<platform>.<target>.<arch>.<so|dll>`; on macOS a `libwane.macos.<target>.framework` holding a universal binary (`arch=universal`), the form Godot's exporter signs. `native/wane.gdextension` has `entry_symbol = "wane_library_init"`, `compatibility_minimum = "4.5"`, `reloadable = false`. `ci/build_native.sh` builds `template_debug` by default (the editor binary and the headless tests load the debug entries), or `template_release` or both; it logs to a file and prints one line, or the last 40 log lines and a non-zero exit.
3. **The switch.** The core asks one function, `NativeBackend.use_native()`, true when the mode is not off and the library is loaded with the expected version. The mode is read once, by the `NativeBoot` autoload (`game/native/native_boot.gd`, the only place that touches `OS` and `ProjectSettings`, which the core may not): the environment variable `WANE_NATIVE` (off, auto, on) wins over the project setting `wane/native/mode`, whose default in `project.godot` is `auto`. Why there: the core cannot read the environment (`tools/ci/core_purity.gd`), an autoload runs in every entry point (the game, `--script` runs, fixtures, benches, gdUnit) without each one calling a setup, and an environment variable lets a CI job choose without editing `project.godot`. Auto means native when it is there: that is the point of the port, and it cannot change a result (Decision 4). Mode on is for CI and for anyone checking a port: if the library is absent, stale or the value is not one of the three words, `NativeBoot` logs an error and quits with exit code 1, so a job that asked for native can never pass on the reference. A port adds one static function per native method to `NativeBackend` (native when `use_native()`, else `NativeRef`), and no caller names a native class. When a library is missing Godot prints two `ERROR` lines at startup ("Error loading extension") and continues; `ci/test.sh --quiet` drops them.
4. **Determinism rules for native code.** (a) Integers only: `int64_t` and `uint32_t`, no `float` or `double`, anywhere in `native/src`; a native function takes and returns Godot `int` (int64) and `PackedInt64Array`, in the core's 1/256 sub-pixel units. (b) No signed overflow: wrap on `uint32_t`/`uint64_t` and convert at the boundary (the reference masks to 32 bits after every operation, ADR-0005, and so does the native code), so an optimiser cannot exploit undefined behaviour differently on gcc, clang and MSVC. (c) No `std::unordered_*`, no pointer-keyed ordering, no iteration in an order that depends on addresses or hashing, in anything that is hashed or that decides a result; use arrays and sorted structures. (d) No time, no threads, no atomics, no `rand`, no locale: randomness only through the core's split streams (`core/rng/`), ported with the same xoshiro128**. (e) Right shifts of negative values, integer division and modulo of negative values use the same rounding as the reference (`Fx.div_floor`, `Fx.div_round`), spelled out in code, never left to the compiler. (f) Identical results on every platform is a test, not a hope: the golden hashes are checked on Linux, Windows and macOS with the switch on (Decision 6). `ci/lint.sh` greps `native/src` for `float`, `double`, `unordered_`, `rand`, `time`, `clock`, `thread`, `atomic` and fails the lint job on a hit outside comments. Compiler flags stay godot-cpp's defaults (no `-ffast-math`, no `-Ofast`, no `/fp:fast`); with no floating point they cannot matter, and if one ever must, this ADR is superseded first.
5. **Keeping the reference honest.** The GDScript `NativeRef` (`core/native/native_ref.gd`) is the specification and what runs when the library is absent. For each native method there is a static function of the same name in `NativeRef`. `tests/unit/core/test_native_parity.gd` (a) pins the reference to vectors computed by an independent Python implementation, so the reference cannot drift together with the port, (b) runs native against those vectors and against a 200-round seeded sweep of full 64-bit patterns, (c) enumerates `ClassDB.class_get_method_list` of the native class and fails on any method that has no reference (only `describe`, build information, is exempt), and (d) checks the dispatch for each mode. A port also adds a differential test of the whole ported function on real state (as `FlatWalk` has for the sweep, ADR-0020 Decision 6): both implementations play the same fixture and compare state at every tick. Each native change bumps `NATIVE_VERSION` in `native/src/native_probe.h` and `NativeBackend.EXPECTED_VERSION` together, so a stale binary on a developer's disk cannot run a replay; a state hash that changes with the same inputs still needs `Simulation.VERSION` + 1 and a re-bless (ADR-0006), and a port must not need either.
6. **CI.** The `test` job installs the pinned SCons, restores the godot-cpp cache (`native/godot-cpp` and `native/.sconsign.dblite`, keyed on runner OS and architecture, the pin file and `ci/build_native.sh`), builds, then runs the whole gate with `WANE_NATIVE=off` (the reference, the coverage gate), then the compile and fixtures stages and the parity suite with `WANE_NATIVE=on` against the same `golden_hashes.txt`. The two `determinism` jobs (Windows, macOS) build the same way and run compile, fixtures and unit twice, off then on. The `lint` job builds nothing and only gains the `native/src` grep. The perf jobs do not build the extension yet; the one that gates the port will (Consequences).

7. **Bind only what is used; cache what was built; check the release library by pointing the debug entries at it.** (a) `native/build_profile.json` lists the engine classes the extension uses (`RefCounted`; `OS`, which godot-cpp's own `print_string.cpp` needs); `native/SConstruct` passes it as godot-cpp's `build_profile`. The full bindings were about a thousand generated files and 13 minutes on a CI runner per target; with the profile a cold debug build is 100 s here (491 s before, on a machine under load) and the release build 26 s after it. A class used by new native code is added to the profile, the build fails on a missing header otherwise. (b) The `native-build` composite action (`.github/actions/native-build`) restores the cache, builds, and saves the cache straight after the build: `actions/cache` saves in a post step that runs only when the job passed, so a job that built and then failed a later step saved nothing, and run 39379127625 built cold in every job. One key per target, runner OS and architecture and the hash of the pin, the SConstruct, the profile and the two scripts; a prefix restore key starts a changed key from the last cache. (c) `ci/native_release_check.sh` no longer copies the release library over the debug one: a macOS framework names its binary after its folder, so the copy held `libwane.macos.template_release` inside `libwane.macos.template_debug.framework` and Godot reported the library not loaded (all 592 fixture shards, run 39379127625). It points the `.debug` entries of `native/wane.gdextension` at the release library for the run and restores the file after, so no debug library is built for that job either.

## Alternatives considered

| Option | Why not |
| --- | --- |
| godot-cpp master built against `godot --dump-extension-api` of 4.7.2 | Binds the exact engine, but master has no release, changes without notice, and a re-dump changes the bindings under the determinism proof. Revisit when godot-cpp tags 4.7. |
| Vendor godot-cpp in the repo | Against rule 10 and the pin discipline of ADR-0001; 180 MB with its build; a pinned commit does the same job. |
| godot-cpp as a git submodule | Needs submodule handling in every checkout and worktree the agents use; the script is one command and verifies the commit. |
| CMake instead of SCons | godot-cpp supports both; SCons is the project's documented path, the same tool as the engine, and the build needs no generator choice per platform. |
| Switch in `project.godot` only | CI would have to rewrite a tracked file per job. The environment variable overrides it; the setting remains the persistent default. |
| Switch as a `Simulation` constructor argument | Every caller (game, fixtures, benches, replay tools, tests) would thread it through; one of them forgetting would run the other implementation unnoticed. |
| Native by default only in exports, GDScript in the editor | Two modes that differ between what is tested and what ships. The same code and the same hashes in both is what the parity tests buy. |
| Float or SIMD-float native code with epsilon comparisons | A desync is a P0 bug (rule 4); the core is integers by rule 2, and integer SIMD is available when a profile asks for it. |

## Feel reason

None directly: the native path gives bit-identical results, so no input, frame or hitbox changes. It serves the movement and combat pillars by making the 60 fps budget reachable in the stress room without cutting enemies, procs or lighting.

## Consequences

- Easier: a profiled function is ported by adding a class to `native/src`, a method to the pair `NativeBackend`/`NativeRef`, and its parity and differential tests; nothing in a caller changes, and the GDScript path remains for debugging (set `WANE_NATIVE=off`).
- Harder: a developer without a C++ toolchain still runs everything (auto falls back), but only CI proves the native path; a port's author builds locally with `ci/build_native.sh`, and must rebuild after pulling a native change (a stale library fails mode on and is ignored by auto because of the version check).
- Build cost: before Decision 7 a cold build on 4 cores took 285 s (godot-cpp's generated bindings are most of it; 13 minutes on a CI runner), a rebuild of the extension alone about 4 s, the debug library is 1.9 MB. The CI cache keeps godot-cpp's objects, so a job pays the cold cost once per cache key. macOS universal compiles each file twice; if that is too slow, build `arch=arm64` on the runner and keep universal for the release build.
- CI risks, unproven until the first run: MSVC (godot-cpp defaults to the static C runtime, `/MT`; `native_probe.cpp` uses only standard C++17 and builds the compiler string with `_MSC_VER`; a warning-as-error flag would show as a failed `build_native`), macOS (universal needs both architectures in the SDK, which Xcode on `macos-14` has; running the x86_64 slice needs Rosetta, which nothing here does: only the arm64 slice is executed), the Windows runner's `scons` on `PATH` (installed by pip next to Python), and the first `ERROR` lines Godot prints when a job without the library imports the project (harmless; the perf jobs).
- The perf job that gates a port (the stress room) must build the extension and run with `WANE_NATIVE=on` when the first port lands; until then `perf-stress` stays as ADR-0020 Decision 14 left it.
- Exports: `wane.gdextension` is already in the project, so `godot --headless --export-release` includes the library for the platform exported; the macOS framework will need an `Info.plist` for notarization, a task for the release phase.
- Revisit when godot-cpp tags 4.7 or later, when the engine pin moves, and when the first port lands (a port's ADR adds its own differential test and the perf numbers).
